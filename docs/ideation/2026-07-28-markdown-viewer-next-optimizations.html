Repository-grounded ideation

Markdown Viewer 下一阶段优化

基于当前代码、测试、近期提交和 2026 年同类工具趋势，筛选出 7 个值得进入需求澄清的方向。排序优先考虑用户价值、证据强度、长期杠杆、实现风险与五个主题轴的覆盖。

Date 2026-07-28 Topic markdown-viewer-next-optimizations Focus 当前项目接下来可以做哪些优化 Mode repo-grounded

Grounding Context

Codebase Context：项目已从轻量预览器扩展为本地 Markdown 工作台，覆盖文件树、大纲、编辑、实时预览、评论、数学与图表、图片资产和多格式导出；核心约束仍是单文件 CLI、零配置、本地优先与 Markdown 文件作为真实数据源。

当前高杠杆问题集中在五处：Markdown HTML 直接进入 DOM；保存冲突主要依赖 mtime 与强制覆盖；评论绑定路径和瞬时文本位置；大型工作区仍以全量扫描与浏览器文件名过滤为主；前端大型全局类、双大纲实现、静态接线测试和独立 WebSocket 端口持续增加维护与部署成本。

外部趋势也指向同一方向：成熟工具正在强化渲染后差异审阅、链接诊断、反向链接、统一命令入口、frontmatter 结构化视图和自动化接口，而不是继续堆叠 Markdown 方言。Marked 官方明确不负责净化输出，Mermaid 与 PlantUML 也要求显式维护安全和网络边界。

Topic Axes

1. 安全与数据可靠性
2. 编辑与知识工作流体验
3. 规模化性能与检索
4. 离线部署与可移植性
5. 工程架构与质量

Ranked Ideas

I1 安全本地工作区 I2 文档事务层 I3 Markdown 智能内核 I4 可回放可靠性系统 I5 单端口可移植运行时 I6 可复现渲染图 I7 耐久审阅层
I1

Trust & Privacy

建立可证明的“安全本地工作区”契约

默认把所有 Markdown、HTML、图表和远程资源视为不可信：Marked 输出经 HTML 净化与 URL 协议白名单，Mermaid 使用 strict/sandbox，原始 HTML 只能显式开启；所有网络请求经过统一能力代理。PlantUML 提供 local / private / ask / disabled 模式，界面持续显示工作区是否完全离线。

Axis
安全与数据可靠性；离线部署与可移植性
Basis
direct: src/public/js/renderer.js:22 设置 sanitize: false，src/public/js/renderer.js:283 将解析结果写入 innerHTML，src/public/js/renderer.js:217 默认请求公共 PlantUML 服务。
external: Marked 明确声明不净化输出；Mermaid 推荐 strict/sandbox 安全级别。
Rationale
“本地优先”不应只描述文件存储位置，还应成为可以通过断网测试和权限状态验证的隐私承诺。该方向同时处理 XSS、隐式网络泄漏、图表可用性和陌生仓库信任问题。
Downsides
可能改变现有原始 HTML 行为；需要设计工作区授权、兼容迁移和远程图片策略，安全策略过严也可能降低文档表现力。
Confidence 97%Complexity Medium–High
I2

Reliability

用“文档事务层”取代强制覆盖

编辑时保存基线内容哈希并追加轻量草稿日志；真实保存通过临时文件、刷新和原子替换完成。外部修改发生后，自动比较基线、本地草稿和磁盘版本，对标题、列表、代码块等语义单元做三方合并，仅让用户处理真正冲突的部分。多文件重命名、链接更新和附件迁移进一步复用同一事务协调器。

Axis
安全与数据可靠性；编辑与知识工作流体验
Basis
direct: src/server.ts:319 以 mtime 判断冲突，src/public/js/editor.js:402 冲突后允许 override: true，src/server.ts:324 直接写目标文件，未保存内容主要依赖 beforeunload。
Rationale
本地文件编辑器最昂贵的失败是内容丢失或覆盖外部修改。事务模型把“不丢内容”从用户必须正确点击的责任，升级为系统保证，并为自动保存、崩溃恢复、跨会话撤销和 AI 修改审阅打底。
Downsides
三方语义合并和跨平台原子写入复杂；需要草稿清理、磁盘空间、恢复 UX 和异常中断测试，首版必须严格限制范围。
Confidence 95%Complexity High
I3

Compounding Platform

建设 Markdown Intelligence Core

抽取 Node 与浏览器共享的纯 Markdown 语义内核，并用 Chokidar 增量维护可删除重建的工作区索引。它统一标题 ID、源码范围、链接、反向链接、图片、frontmatter、图表和诊断；再通过命令注册表对 UI、快捷键、命令面板和 CLI 暴露能力。首批成果可同时包含全文搜索、快速打开、坏链接检查、重命名影响预览和反向链接。

Axis
规模化性能与检索；编辑与知识工作流体验；工程架构与质量
Basis
direct: src/fileUtils.ts:63 串行递归扫描，src/public/js/fileTree.js:66 只匹配文件名，src/fileUtils.ts:119 与 src/public/js/renderer.js:309 维护两套大纲逻辑。
external: VS Code 的链接诊断和 Obsidian 的 Links、Backlinks、Bases、Command Palette 已验证工作区语义层价值。
Rationale
它不是“再加一个搜索功能”，而是让未来一半工作区能力变成同一索引和语义模型的查询。每增加一种提取器，搜索、诊断、重构、导航和自动化都会同步增强。
Downsides
范围极易膨胀；必须先锁定最小语义模型与首批 2–3 个用户结果，避免演变成插件平台或私有数据库。
Confidence 93%Complexity High
I4

Quality Flywheel

建立可回放的真实工作区可靠性系统

用微型 Markdown 工作区和事件脚本直接启动最终 mdviewer.js，通过无头浏览器回放打开、编辑、外部修改、保存冲突、重命名、符号链接、评论定位、图表失败、实时通道断线和跨平台路径。为文件事件、保存、渲染和评论操作记录不含正文的因果轨迹；每次事故同时沉淀为回归场景和 docs/solutions/ 经验。

Axis
工程架构与质量；安全与数据可靠性
Basis
direct: tests/test-editor-smoke.js:6 读取静态源码，tests/test-editor-smoke.js:30 主要检查脚本接线，未启动真实服务器或浏览器。现有测试也未覆盖文件监听、WebSocket、保存冲突和真实图表渲染。
external: Playwright 官方提供多浏览器、自动等待、截图和 Trace Viewer，适合回放端到端事故。
Rationale
本地文件应用最难复现的是时序事故，而非纯函数错误。该系统让每次真实故障都变成永久资产，同时保护 I1–I3 这类高风险底座改造。
Downsides
CI 时间和跨平台夹具维护成本会上升；需要避免轨迹记录正文或隐私内容，并控制场景数量以防测试套件失控。
Confidence 92%Complexity Medium
I5

Portability

收敛为单端口、可解释降级的运行时

删除固定 HTTP + 5080 的独立 WebSocket 端口，将文件变化通知改为同端口 SSE 或同端口 WebSocket upgrade；不可用时降级为带 ETag 的条件轮询，并明确显示实时同步状态。启动时同时生成能力清单，解释本地 PlantUML、远程图表、事件通道和导出能力，而不是静默降级。

Axis
离线部署与可移植性
Basis
direct: src/server.ts:551 启动独立 WebSocket 服务，src/public/js/app.js:212 由浏览器计算偏移端口；Docker 文档只暴露 HTTP 端口。当前实时流量主要是服务端单向广播，SSE 与同端口升级均更贴合部署。
Rationale
它解决“页面能打开但实时刷新坏了”的隐性故障，显著降低 Docker、HTTPS、反向代理、局域网与防火墙配置成本，同时让用户知道当前是否仍在实时同步。
Downsides
需要兼容旧启动脚本和端口逻辑；SSE 的事件补偿、代理缓冲和浏览器连接限制要经过真实部署测试。
Confidence 91%Complexity Medium
I6

Performance & Consistency

把预览与导出变成可复现的增量渲染图

按语义块生成内容指纹，建立“Markdown → 安全 HTML → Prism / KaTeX / Mermaid / PlantUML → 预览与导出”的依赖图。只重算受影响块，复用未变化的 DOM 与图表；预览、HTML、Word、PNG 和打印共享同一份渲染清单，记录主题、依赖版本、安全模式和资源策略。

Axis
规模化性能与检索；工程架构与质量
Basis
direct: src/public/js/renderer.js:264 每次解析完整内容，src/public/js/renderer.js:287 清空并替换容器，src/public/js/renderer.js:227 串行渲染全部 Mermaid；多个导出入口再次强制完整渲染。依赖声明与 vendored 实际版本还存在漂移。
Rationale
该方向同时提升大文档延迟、图表重算、滚动稳定性和导出一致性；新增渲染器只需声明依赖和缓存键，不必重新设计性能策略。
Downsides
实现成本高且容易过度工程化；应先建立性能基线，只有大文档和图表场景证明收益后再推进块级失效。
Confidence 84%Complexity High
I7

Differentiated Review

让评论升级为耐久的内容审阅层

评论锚点从文件路径、元素 ID 和字符偏移升级为“文档指纹＋标题路径＋前后文＋文本哈希”的复合定位；存储采用追加事件日志和原子快照，正文变动或文件重命名后自动重新定位，低置信度评论进入待确认列表。评论可附带标准 diff 建议，但不污染 Markdown 正文，默认不持久化 IP。

Axis
编辑与知识工作流体验；安全与数据可靠性
Basis
direct: 当前评论整体同步覆盖 comments.json，按文件路径、元素 ID 与文本位置持久化，渲染刷新后再重新包裹高亮；文件变更监听不会迁移评论归属。
Rationale
评论是项目已有的差异化能力，但当前锚点无法经受重命名和内容重排。耐久锚点可把它从页面装饰升级为长期本地审阅协议，并与 I2 的事务和 I3 的语义内核形成复利。
Downsides
重新定位是启发式问题，必须展示置信度与人工确认；旧评论迁移和事件日志压缩也需要清晰的数据版本策略。
Confidence 83%Complexity Medium–High

Rejection Summary

#IdeaReason Rejected
1独立工作区事务协调器已并入 I2；作为文档事务层的多文件扩展更完整。
2单独的工作区编译索引已并入 I3；仅做索引会错失共享语义内核和命令入口的复利。
3单独的 Markdown 重构引擎已并入 I3；它是语义模型上的首批产品结果，不应成为另一套底座。
4工作区瞬移框已并入 I3；统一入口有价值，但缺少索引与命令图时只是更大的搜索框。
5渐进式文件树启动作为 I3 的规模化实现策略保留，不足以单独成为长期产品方向。
6虚拟 frontmatter 表格/看板有外部验证但属于较大产品扩张；应在 I3 稳定后单独 brainstorm。
7共享大纲/链接语义模块已并入 I3；单独做只解决重复逻辑，价值低于完整语义内核。
8命令注册表与 CLI已并入 I3；作为内核的控制面比独立工具栏重构更有杠杆。
9PlantUML 隐私代理已并入 I1；单点解决 PlantUML 无法覆盖 HTML、图片和其他网络能力。
10离线依赖自动供应链证据充分，但更适合作为 I1/I6 的工程保障，不独立占据 survivor 名额。
11自解压内容寻址资源包当前 6.6MB 产物尚不足以证明用户价值高于缓存、解压和清理复杂度。
12原生 ES Module 迁移必要但低于 ambition floor；是 I3/I4 的实施手段，不是用户可选择的方向。
13Viewer/Editor 块级原地编辑创新但交互与定位风险高，且依赖 I3；更适合后续单独 brainstorm。
14工作区黑匣子轨迹已并入 I4；没有真实发布物回放时，轨迹自身价值有限。
15可复现导出清单已并入 I6；与增量渲染共享依赖图和版本清单更强。
16附件生命周期与孤立图片诊断作为 I3 的首批诊断和 I2 的事务用例保留，不单独晋级。
17单独建立 solutions 与性能预算已并入 I4；只有和事故回放绑定，知识沉淀才会持续发生。

独立依据核验任务未在时限内完成；最终筛选由主代理基于 331 条仓库证据逐项复核，并对高复杂度组合保守下调置信度。
